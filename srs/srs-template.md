## 1. Введение {#1-introduction}

Документ SRS описывает бизнес- и программные требования к веб-приложению **TypePulse**. Документ предназначен для заказчика, менеджера проекта, разработчиков и проверяющих. Он фиксирует **что** должна делать система, без детализации реализации (см. будущий SDD).

### 1.1 Назначение документа {#11-document-purpose}

SRS задаёт единую базу согласования требований между заказчиком и командой разработки. Разработчики используют документ для проектирования и реализации; QA — для построения тест-кейсов; заказчик — для приёмки. Документ определяет наблюдаемое поведение системы, критерии приёмки и ограничения (стек, сроки, границы MVP).

### 1.2 Область применения продукта {#12-product-scope}

**TypePulse** — веб-приложение (Web) для оценки и улучшения навыков набора текста на клавиатуре.

**Бизнес-цели:**
- дать пользователю объективную метрику скорости (WPM) и точности набора;
- обеспечить регулярную практику через короткие тренировки и историю прогресса;
- снизить порог входа (без установки Desktop-клиента).

**Входит в scope (MVP):**
- регистрация/вход (учётная запись);
- тренировка: показ текста, ввод, подсветка ошибок, таймер;
- расчёт WPM, точности (%), числа ошибок;
- выбор языка текста (русский / английский) и длительности (30 / 60 / 120 с);
- сохранение результатов и просмотр истории;
- простой рейтинг (топ по среднему WPM).

**Не входит в scope (v1):**
- мобильное нативное приложение;
- интеграция с внешними LMS / Moodle;
- платные тарифы и реклама;
- обучение слепой печати с анимацией пальцев (может быть в релизе 2);
- многопользовательские «заезды» в реальном времени.

**Тип проекта:** Web-приложение.  
**Язык разработки:** Java (предпочтительно Spring Boot).  
**Язык описания требований:** русский (Markdown + SysMLv2 для GUI/контекста).

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

TypePulse — **новый самостоятельный продукт** (не замена существующей корпоративной системы). Пользователь работает через браузер; серверная часть хранит учётные записи, тексты и результаты.

Контекст (см. также SysML в `srs/sysml/TypePulseContext.sysml`):

```
[Пользователь] --браузер--> [TypePulse Web UI] --HTTP/REST--> [TypePulse Backend (Java)]
                                                      |
                                                      v
                                              [БД результатов/текстов]
```

Внешние сервисы в MVP **не обязательны**. Опционально (релиз 2): OAuth (Google/GitHub), CDN для статики.

### 2.2 Функции продукта {#22-product-functions}

1. **Аутентификация** — регистрация, вход, выход.
2. **Настройка тренировки** — язык, длительность, сложность текста.
3. **Сеанс тренировки** — отображение текста, приём ввода, подсветка ошибок, таймер.
4. **Расчёт метрик** — WPM, точность, ошибки, время.
5. **История** — список прошлых результатов пользователя.
6. **Рейтинг** — таблица лидеров по среднему/лучшему WPM.
7. **Профиль** — краткая статистика (кол-во тренировок, лучший WPM, средняя точность).

### 2.3 Ограничения продукта {#23-product-constraints}

1. Система **должна** быть реализована как Web-приложение.
2. Серверная часть **должна** быть написана на **Java**.
3. Клиент **должен** работать в актуальных версиях Chrome, Firefox, Edge (последние 2 major-версии).
4. MVP **должен** укладываться в учебный семестр дисциплины ЖЦРПО.
5. Персональные данные (логин, email, результаты) **должны** храниться только в рамках приложения; передача третьим лицам без согласия запрещена.
6. UI-прототипы **должны** быть описаны на SysMLv2 и сохранены в PNG (`srs/mockups/`).

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Класс | Описание | Цели | Частота |
|-------|----------|------|---------|
| Ученик / студент | Базовый навык ПК, русский/английский | Улучшить скорость к экзаменам, набору конспектов | 2–5 раз/нед. |
| Офисный пользователь | Средний навык, работа с документами | Поддерживать навык, измерить прогресс | 1–3 раза/нед. |
| Преподаватель / тренер | Организует практику | Смотреть прогресс (в MVP — через рейтинг/историю ученика самим учеником) | по необходимости |
| Администратор (системный) | Техническая роль | Управление текстами, модерация (минимум в MVP) | редко |

В MVP роли: **Гость** (просмотр лендинга), **Пользователь** (тренировки + история), **Администратор** (CRUD текстов — можно отложить на релиз 2, тексты — из предустановленного набора).

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

| # | Допущение / зависимость | Риск при нарушении |

| A2 | Браузер поддерживает современный JS/CSS | Деградация UI |

## 3. Требования {#3-requirements}

Формат ID: `REQ-[AREA]-[NNN]`.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

Основные экраны (мокапы PNG + SysML):

| Экран | Файл PNG | SysML |
|-------|----------|-------|
| Главная / старт | `srs/mockups/01-home.png` | `TypePulseUI::HomeScreen` |
| Настройка тренировки | `srs/mockups/02-setup.png` | `TypePulseUI::SetupScreen` |
| Сеанс тренировки | `srs/mockups/03-training.png` | `TypePulseUI::TrainingScreen` |
| Результат | `srs/mockups/04-result.png` | `TypePulseUI::ResultScreen` |
| История / рейтинг | `srs/mockups/05-history-leaderboard.png` | `TypePulseUI::HistoryScreen` |

**REQ-INT-001**  
- **Title:** Консистентность UI  
- **Statement:** Система должна предоставлять единый набор экранов согласно мокапам: навигация (Главная, Тренировка, История, Рейтинг, Профиль), читаемый контраст текста, явную индикацию ошибок ввода.  
- **Rationale:** Снижает когнитивную нагрузку во время скоростного набора.  
- **Acceptance Criteria:** Все экраны MVP присутствуют; отклонение от мокапа согласовано с заказчиком.  
- **Verification Method:** Inspection / Demonstration  

**REQ-INT-002**  
- **Title:** Фокус на поле ввода  
- **Statement:** На экране тренировки система должна автоматически устанавливать фокус на область ввода при старте сеанса и не перекрывать эталонный текст всплывающими окнами.  
- **Acceptance Criteria:** После нажатия «Старт» пользователь может печатать без дополнительного клика.  
- **Verification Method:** Test  

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-003**  
- **Statement:** Система должна принимать ввод с физической или экранной клавиатуры через стандартные события браузера. Специализированное оборудование (механические макросы, HID-устройства вне клавиатуры) не требуется.  
- **Verification Method:** Test  

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-004**  
- **Title:** HTTP API бэкенда  
- **Statement:** Backend должен предоставлять REST API для: регистрации/логина, старта/завершения тренировки, получения истории и рейтинга. Формат обмена — JSON, протокол — HTTPS в продакшене (HTTP допустим в локальной разработке).  
- **Acceptance Criteria:** Описаны эндпоинты в README или OpenAPI (к моменту реализации); клиент успешно выполняет сценарий «тренировка → сохранение результата».  
- **Verification Method:** Test  

### 3.2 Функциональные требования {#32-functional}

**REQ-FUNC-001** — Регистрация и вход  
- **Statement:** Система должна позволять пользователю создать учётную запись (логин, email, пароль) и выполнять вход/выход.  
- **Rationale:** Нужна привязка истории и рейтинга к личности.  
- **Acceptance Criteria:**  
  - регистрация с уникальным email успешна;  
  - повторная регистрация с тем же email отклоняется с понятным сообщением;  
  - после входа доступны тренировка и история.  
- **Verification Method:** Test  

**REQ-FUNC-002** — Настройка тренировки  
- **Statement:** Перед стартом система должна позволять выбрать язык текста (RU/EN), длительность (30/60/120 с) и уровень сложности (лёгкий / средний / сложный).  
- **Acceptance Criteria:** Выбранные параметры отображаются на экране тренировки и влияют на выдаваемый текст.  
- **Verification Method:** Test  

**REQ-FUNC-003** — Проведение тренировки  
- **Statement:** Система должна отображать эталонный текст, принимать посимвольный ввод, визуально отмечать верные и неверные символы, вести обратный отсчёт выбранной длительности и завершать сеанс по таймеру или по исчерпанию текста.  
- **Acceptance Criteria:** Ошибочный символ подсвечивается иначе, чем верный; по окончании открывается экран результата.  
- **Verification Method:** Demonstration / Test  

**REQ-FUNC-004** — Расчёт метрик  
- **Statement:** По завершении сеанса система должна рассчитать и показать:  
  - **WPM** = (число правильно введённых символов / 5) / (время_в_минутах);  
  - **точность** = (правильные символы / все введённые символы) × 100%;  
  - число ошибок;  
  - фактическое время.  
- **Rationale:** Единое правило исключает споры при приёмке (в т.ч. для русского текста).  
- **Acceptance Criteria:** Для контрольного ввода (заранее известный текст и время) метрики совпадают с эталоном ±1 WPM и ±0.5% точности.  
- **Verification Method:** Test  

**REQ-FUNC-005** — Сохранение результата  
- **Statement:** Система должна сохранять результат авторизованного пользователя (дата, WPM, точность, язык, длительность, сложность).  
- **Acceptance Criteria:** После обновления страницы результат виден в истории.  
- **Verification Method:** Test  

**REQ-FUNC-006** — История  
- **Statement:** Система должна показывать пользователю список его результатов (не менее последних 50), отсортированный по дате (новые сверху).  
- **Verification Method:** Test  

**REQ-FUNC-007** — Рейтинг  
- **Statement:** Система должна отображать таблицу лидеров не менее чем из топ-20 пользователей по лучшему WPM (при равенстве — по точности).  
- **Verification Method:** Test  

**REQ-FUNC-008** *(релиз 2, отложено)* — Управление текстами администратором  
- **Statement:** Администратор должен иметь возможность добавлять/удалять эталонные тексты.  
- **Status:** Отложено  

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

**REQ-PERF-001**  
- **Statement:** Ввод символа на экране тренировки должен отражаться в UI не позднее чем через **100 мс** после события клавиатуры на машине разработчика/демо (локальный профиль).  
- **Verification Method:** Test / Analysis  

**REQ-PERF-002**  
- **Statement:** Страницы истории и рейтинга должны открываться не более чем за **2 с** при объёме данных до 10 000 результатов (локальная/учебная среда).  
- **Verification Method:** Test  

#### 3.3.2 Безопасность {#332-security}

**REQ-SEC-001**  
- **Statement:** Пароли должны храниться только в виде криптографического хеша (не в открытом виде).  
- **Verification Method:** Inspection  

**REQ-SEC-002**  
- **Statement:** Пользователь должен иметь доступ только к своей истории; чужие детальные результаты (кроме данных рейтинга: ник + WPM) недоступны.  
- **Verification Method:** Test  

#### 3.3.3 Надёжность {#333-reliability}

**REQ-REL-001**  
- **Statement:** При потере соединения во время тренировки система должна корректно завершить или отменить сеанс с сообщением пользователю и не записывать частично повреждённый результат как успешный.  
- **Verification Method:** Test  

#### 3.3.4 Доступность {#334-availability}

**REQ-AVAIL-001**  
- **Statement:** В учебном развёртывании система должна быть доступна в согласованные окна демонстрации (не менее 95% времени окна демо). Полноценный SLA 24/7 для MVP не требуется.  
- **Verification Method:** Demonstration  

#### 3.3.5 Наблюдаемость {#335-observability}

**REQ-OBS-001**  
- **Statement:** Backend должен писать журнал ошибок сервера (уровень ERROR) с меткой времени и без паролей/токенов в открытом виде.  
- **Verification Method:** Inspection  

### 3.4 Соответствие стандартам {#34-compliance}

**REQ-COMP-001**  
- **Statement:** Документация требований должна вестись по шаблону кафедры (ISO/IEC/IEEE 29148 в учебной адаптации).  
- **Verification Method:** Inspection  

**REQ-COMP-002**  
- **Statement:** Обработка персональных данных должна соответствовать базовым принципам минимизации: собираются только логин, email, пароль (хеш) и результаты тренировок.  
- **Verification Method:** Analysis  

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**REQ-INST-001**  
- **Statement:** Проект должен запускаться локально инструкцией из README (JDK 17+, сборка Maven/Gradle, команда запуска).  
- **Verification Method:** Demonstration  

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

#### 3.5.3 Распределение {#353-distribution}

MVP: односерверное развёртывание (локально или один хост). Геораспределение не требуется.

#### 3.5.4 Сопровождаемость {#354-maintainability}

**REQ-MAINT-001**

#### 3.5.5–3.5.6 Повторное использование и переносимость

Допускается использование стандартных библиотек Java/Spring. Целевая переносимость: Windows/Linux для сервера; любой десктоп-браузер для клиента.

#### 3.5.7 Стоимость {#357-cost}

Учебный проект: бюджет инфраструктуры ≈ 0 (локальный запуск). Платные API не используются в MVP.

#### 3.5.10 Управление изменениями {#3510-change-management}

Изменения требований оформляются замечаниями в Pull Request (напарник → преподаватель). Неконструктивные предложения отклоняются с обоснованием в обсуждении PR. После merge обновляется версия SRS и история изменений.
