# ADR-0001: Use Spring Boot monolith for TypePulse

## Контекст и постановка задачи

SRS фиксирует Web-приложение на Java с ограниченным учебным сроком и одной небольшой командой. Нужно выбрать архитектурный стиль поставки: монолит, модульный монолит/несколько сервисов или отдельный frontend + backend с самого начала.

Вопрос: **какой архитектурный стиль минимизирует срок MVP при сохранении требований SRS (тренировка, метрики, история, рейтинг)?**

Связь: REQ-FUNC-001…007, REQ-INST-001, REQ-BUILD-001; SDD VIEW-002, VIEW-008.

## Драйверы решения

* Срок MVP и длина итерации 10 рабочих дней (см. SDD, план v2)
* Обязательный язык Java на сервере
* Компетенции команды (учебный стек Spring)
* Простота локального запуска для демонстрации преподавателю
* Низкая операционная сложность (один процесс)

## Рассмотренные варианты

* Spring Boot modular monolith (один deployable)
* Микросервисы (auth / training / ranking отдельно)
* Классический Java EE / Jakarta EE application server без Spring

## Итог решения

Выбранный вариант: **Spring Boot modular monolith**, потому что единственный вариант, который одновременно удовлетворяет сроку MVP, требованию Java и простоте демо без оркестрации сервисов.

### Последствия

* Хорошо, потому что один артефакт (`jar`), проще CI и отладка
* Хорошо, потому что слои Controller/Service/Repository достаточно разделяют зоны ответственности внутри монолита
* Плохо, потому что при росте нагрузки ranking и training нельзя масштабировать независимо
* Нейтрально, потому что позже можно выделить ranking в сервис без смены доменной модели

### Подтверждение

* Структура пакетов `auth|training|results|ranking|texts` проверяется на code review
* README содержит одну команду запуска; демо идёт с одним процессом

## Плюсы и минусы вариантов

### Spring Boot modular monolith

* Хорошо, потому что быстрый старт и богатая экосистема Security/Data
* Хорошо, потому что соответствует учебным материалам и навыкам команды
* Плохо, потому что риск «комка» кода без дисциплины модулей

### Микросервисы

* Хорошо, потому что изоляция отказов и независимое масштабирование
* Плохо, потому что сеть, деплой и согласование контрактов съедят весь запас итераций
* Плохо, потому что для MVP TypePulse избыточно

### Java EE / Jakarta EE без Spring

* Хорошо, потому что стандарты платформы
* Плохо, потому что дольше поднять демо-окружение в учебном контексте
* Нейтрально, потому что функционально достижимо то же самое
