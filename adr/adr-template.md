# Выбор Spring Boot-монолита для веб-приложения TypePulse

## Контекст и постановка задачи

По согласованному SRS TypePulse — веб-приложение на Java: тренировка печати, расчёт WPM и точности, история результатов и рейтинг. Срок учебного MVP ограничен тремя итерациями по 10 рабочих дней, команда небольшая. Нужно выбрать архитектурный стиль поставки так, чтобы уложиться в дедлайн без лишней операционной сложности.

Какой стиль архитектуры минимизирует срок MVP при выполнении требований SRS (Java, Web, история, рейтинг)?

Связанные артефакты: REQ-FUNC-001…007, REQ-INST-001; `sdd/sdd-template.md` (VIEW-002, VIEW-008).

## Драйверы решения

* Срок MVP и отказ Заказчика сдвигать deadline (лаб. №4, раунд 2)
* Обязательный язык серверной части — Java
* Учебные компетенции команды (Spring)
* Простой локальный запуск для демонстрации преподавателю (REQ-INST-001)
* Низкая стоимость сопровождения (один процесс развёртывания)

## Рассмотренные варианты

* Spring Boot modular monolith (один deployable JAR)
* Микросервисы (отдельные сервисы auth / training / ranking)
* Jakarta EE / Java EE application server без Spring

## Итог решения

Выбранный вариант: «Spring Boot modular monolith», потому что он единственный одновременно удовлетворяет сроку MVP, требованию Java и простоте демо без оркестрации нескольких сервисов.

### Последствия

* Хорошо, потому что один артефакт (`jar`), проще CI, отладка и демонстрация
* Хорошо, потому что слои Controller → Service → Repository разделяют ответственность внутри монолита
* Плохо, потому что при росте нагрузки нельзя независимо масштабировать ranking и training
* Нейтрально, потому что позже ranking можно выделить в отдельный сервис без смены доменной модели

### Подтверждение

Соблюдение решения проверяется code review структуры пакетов `auth | training | results | ranking | texts`, наличием одной команды локального запуска в README и соответствием представлениям SDD VIEW-002 / VIEW-008 при демонстрации (один JVM-процесс).

## Плюсы и минусы вариантов

### Spring Boot modular monolith

Один Spring Boot-приложение с логическими модулями по доменам.

* Хорошо, потому что быстрый старт и экосистема Spring Security / Spring Data
* Хорошо, потому что соответствует учебному стеку и навыкам команды
* Нейтрально, потому что модульность держится дисциплиной пакетов, а не отдельными репозиториями
* Плохо, потому что без дисциплины возможен «комок» кода в одном модуле

### Микросервисы

Отдельные сервисы и деплой для auth, training, ranking.

* Хорошо, потому что изоляция отказов и независимое масштабирование
* Плохо, потому что сеть, контракты и деплой съедят запас итераций
* Плохо, потому что для MVP TypePulse избыточно относительно бюджета Заказчика

### Jakarta EE / Java EE application server без Spring

Классический application server и стандарты платформы.

* Хорошо, потому что опора на спецификации Java EE / Jakarta EE
* Плохо, потому что дольше поднять демо-окружение в учебном контексте
* Нейтрально, потому что функционально достижим тот же результат ценой большего времени

## Дополнительная информация

Пересмотреть решение, если появятся независимые команды на подсистемы или нагрузка существенно выше демо-группы.
