# ADR-0003: Server-rendered UI (Thymeleaf) and cookie session auth

## Контекст и постановка задачи

Нужно реализовать UI по мокапам (`srs/mockups/`) и аутентификацию (REQ-FUNC-001, REQ-SEC-*). Варианты: SPA (React/Vue) + JWT API, либо server-rendered страницы + session cookie. На экране тренировки всё равно потребуется JavaScript для подсветки и live-WPM (REQ-PERF-001).

Вопрос: **как закрыть UI и auth к дедлайну I3 без раздувания фронтенд-инфраструктуры?**

Связь: SDD VIEW-004, VIEW-005; ADR-0001; SYS-F-01, SYS-F-02, SYS-NF-01.

## Драйверы решения

* Срок и стоимость (Заказчик отказался сдвигать deadline и сильно увеличивать бюджет)
* Появление Junior на I2–I3 — проще давать задачи по шаблонам страниц, чем по SPA-сборке
* Безопасность: пароли только как хеш; без лишней поверхности JWT refresh
* Мокапы — многостраничный web, не сложное SPA-приложение

## Рассмотренные варианты

* Thymeleaf + Spring Security form login (session cookie) + JS на Training screen
* REST API + SPA (React) + JWT
* REST API + vanilla HTML/JS без шаблонизатора, своя auth

## Итог решения

Выбранный вариант: **Thymeleaf + Spring Security form-login (cookie session) + точечный JS на тренировке**, потому что быстрее даёт экраны MVP, упрощает задачи Junior и достаточен для требований безопасности MVP.

### Последствия

* Хорошо, потому что меньше tooling (нет обязательного Node CI для UI)
* Хорошо, потому что CSRF/session из коробки Spring Security
* Плохо, потому что live-UI тренировки всё равно требует аккуратного JS (не «чистый» SSR)
* Плохо, потому что отдельным мобильным клиентам позже понадобится API-слой
* Нейтрально, потому что при необходимости можно добавить JSON API рядом с MVC

### Подтверждение

* Сценарий: register → login → start training → finish → history без ручной подстановки токенов
* На Training screen измеряется отклик подсветки (цель ≤100 ms локально)
* Пароли в БД только как hash (инспекция / тест)

## Плюсы и минусы вариантов

### Thymeleaf + session auth + JS

* Хорошо, потому что совпадает с монолитом ADR-0001
* Хорошо, потому что Junior может верстать формы History/Custom texts по мокапам
* Плохо, потому что меньше «вау»-SPA, но Заказчик это не требовал

### React SPA + JWT

* Хорошо, потому что чёткое разделение front/back
* Плохо, потому что + assembliя, CORS, refresh-токены — риск сорвать I3
* Плохо, потому что стоимость выше при запрете Заказчика раздувать бюджет

### Vanilla HTML + самописная auth

* Хорошо, потому что минимум зависимостей
* Плохо, потому что легко ошибиться в security
* Плохо, потому что больше ручной работы, чем с Spring Security

## Дополнительная информация

Сервер остаётся источником истины для WPM (VIEW-006): клиентский live-WPM — индикатор, финальные цифры пересчитываются на `finish`. Решение принято вместе с планом v2 (SDD §F–G).
